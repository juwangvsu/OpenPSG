# PSG LiDAR Enhancement

`psg_lidarenh` extends `psgtr_hf` 0.5.2 with a global LiDAR-token branch that
improves only:

- subject 2D box prediction;
- object 2D box prediction;
- predicate prediction.

It intentionally does **not** add 3D box heads, 3D losses, point-level labels,
object-level 3D annotations, or camera-LiDAR projection. Object classes and
panoptic masks remain on the pretrained camera-only PSGTR path.

## Model

```text
RGB image -> pretrained PSGTR -> triplet queries
                                  |  \
                                  |   +-> camera-only classes and masks
                                  |
LiDAR scan -> voxel tokens -------+-> global cross-attention
                                      |
                                      +-> subject 2D box
                                      +-> predicate
                                      +-> object 2D box
```

Every query attends to every retained LiDAR voxel token. The fusion gate starts
at zero, so bootstrapping initially reproduces PSGTR boxes and predicates
exactly. Fine-tuning opens the gate and trains the LiDAR branch through the
existing 2D box and relation losses.

## Install

Install the previously generated PSGTR-HF 0.5.2 package first, then this one:

```bash
python3 -m pip install -e /path/to/psgtr_hf --no-deps
python3 -m pip install -e . --no-deps
```

## Convert KITTI-360

The converter is configured for the raw root described in the request:

```text
/data/jwang/datasets/kitti360/
├── calibration/
├── data_2d_raw -> KITTI-360/data_2d_raw/
├── data_2d_semantics/
├── data_3d_bboxes/
├── data_3d_raw -> KITTI-360/data_3d_raw/
├── data_3d_semantics/
└── data_poses/
```

Only these inputs are consumed:

```text
data_2d_raw/
data_2d_semantics/
data_3d_raw/
```

The 3D bounding boxes, fused 3D annotations, poses, and calibration files are
not read.

Run:

```bash
psg-lidarenh-convert-kitti360 \
  --kitti360-root /data/jwang/datasets/kitti360 \
  --source-openpsg-json /data/jwang/datasets/psg/psg_train_val.json \
  --output-root /data/jwang/datasets/kitti360_psg \
  --seq 0 \
  --link-mode symlink \
  --relation-mode spatial2d
```

Equivalent source invocation:

```bash
python3 examples/convert_kitti360.py \
  --kitti360-root /data/jwang/datasets/kitti360 \
  --source-openpsg-json /data/jwang/datasets/psg/psg_train_val.json \
  --output-root /data/jwang/datasets/kitti360_psg
```

### Category mapping and pretrained rows

The converter reads `thing_classes`, `stuff_classes`, and `predicate_classes`
from the original OpenPSG JSON. It does not create a compact KITTI vocabulary,
so the pretrained PSGTR class and predicate head dimensions remain unchanged.

Default mappings include:

```text
KITTI road          -> OpenPSG road
KITTI sidewalk      -> OpenPSG pavement-merged
KITTI building      -> OpenPSG building-other-merged
KITTI wall          -> OpenPSG wall-other-merged
KITTI fence         -> OpenPSG fence-merged
KITTI sky           -> OpenPSG sky-other-merged
KITTI person/rider  -> OpenPSG person
KITTI car           -> OpenPSG car
KITTI truck         -> OpenPSG truck
KITTI bus           -> OpenPSG bus
KITTI train         -> OpenPSG train
KITTI motorcycle    -> OpenPSG motorcycle
KITTI bicycle       -> OpenPSG bicycle
KITTI traffic light -> OpenPSG traffic light
```

Potentially misleading mappings are disabled by default:

```text
pole         -> light
traffic sign -> stop sign
vegetation   -> tree-merged
terrain      -> grass-merged
```

They can be enabled explicitly with:

```bash
--include-approximate-mappings
```

`category_mapping.json` records every included and ignored KITTI semantic ID,
the final OpenPSG category ID, and whether the mapping is exact, compatible, or
approximate.

### Relations generated by the converter

KITTI-360 has no OpenPSG scene-graph relation annotations. By default, the
converter generates conservative 2D pseudo-labels using only predicates that
already exist in the pretrained OpenPSG vocabulary:

```text
over
beside
on
in
```

These are bootstrap labels, not equivalent to human scene-graph annotations.
They do not generate activity predicates such as `driving`, `riding`,
`parked on`, or `about to hit`. Fine-tuning on manually checked relations is
recommended for meaningful predicate evaluation.

To emit no pseudo-relations:

```bash
--relation-mode none --no-require-relations
```

The standard training loader filters relation-empty images, so this mode is
only useful when relations will be added afterward.

## Train from PSGTR

```bash
CUDA_VISIBLE_DEVICES=4,5,6,7 torchrun \
  --standalone \
  --nproc-per-node=4 \
  examples/train.py \
  --psgtr-checkpoint work_dirs/psgtr_hf/checkpoint-0024 \
  --data-root /data/jwang/datasets/kitti360_psg \
  --annotation-file /data/jwang/datasets/kitti360_psg/annotations/psg_train_val.json \
  --lidar-manifest /data/jwang/datasets/kitti360_psg/lidar/manifest.json \
  --output-dir work_dirs/psg_lidarenh_kitti360 \
  --batch-size 1 \
  --gradient-accumulation-steps 2 \
  --num-workers 2 \
  --amp
```

Training evaluates the same deterministic 200 train and 200 validation samples
every four epochs. It reports PQ/SQ/RQ and predicate R/mR at 20, 50, and 100.

### Training and initialization modes

The default remains full fine-tuning: the pretrained PSGTR branch and the new
LiDAR branch are both trainable, with the convolutional image backbone using
`--backbone-lr`.

Freeze only the pretrained ResNet image backbone:

```bash
--freeze-image-backbone
```

The transformer, learned queries, class/relation/box heads, mask branch, and
LiDAR branch remain trainable. The frozen ResNet is also kept in evaluation
mode so BatchNorm running statistics do not change.

Freeze the entire pretrained PSGTR branch and train only the LiDAR modules:

```bash
--freeze-psgtr
```

Only these modules are trainable in this mode:

```text
lidar_encoder
lidar_query_fusion
```

The frozen PSGTR branch remains in evaluation mode while the LiDAR branch is in
training mode.

Reinitialize PSGTR while retaining and freezing the pretrained image backbone:

```bash
--reinitialize-psgtr-freeze-backbone
```

This copies only the checkpoint's convolutional ResNet weights. It randomly
initializes the transformer encoder/decoder, learned queries, object and
predicate classifiers, 2D box heads, mask branch, and LiDAR modules. The copied
ResNet is frozen.

The three options are mutually exclusive. Checkpoints store the selected mode
in `config.json`, `training_state.pt`, and `training-configuration.json`.
`--resume auto` restores it automatically and rejects attempts to change the
mode mid-run.

Resume:

```bash
--resume auto
```

## LiDAR manifest

The converter produces:

```json
{
  "point_feature_count": 4,
  "samples": {
    "9001234": {
      "lidar_file": "/data/jwang/datasets/kitti360/data_3d_raw/2013_05_28_drive_0009_sync/velodyne_points/data/0000001234.bin",
      "sequence": "2013_05_28_drive_0009_sync",
      "frame": 1234
    }
  }
}
```

There is intentionally no `boxes_3d`, `boxes_3d_valid`, calibration, or pose
field.


## Sequence selection and frame limits

`--seq` selects exactly one KITTI-360 drive. It accepts the numeric sequence
ID and defaults to `0`:

```text
--seq 0 -> 2013_05_28_drive_0000_sync
--seq 1 -> 2013_05_28_drive_0001_sync
--seq 9 -> 2013_05_28_drive_0009_sync
```

Only annotated train/validation frames from the selected sequence are read from
the official split lists.

When `--max-frames N` is supplied, `N` is the number of successfully converted
training frames. The converter additionally keeps `ceil(0.1 * N)` successfully
converted validation frames from the same sequence. Missing LiDAR files,
filtered images, or relation-empty frames do not consume either kept-frame
quota.

For example:

```bash
psg-lidarenh-convert-kitti360 \
  --kitti360-root /data/jwang/datasets/kitti360 \
  --source-openpsg-json /data/jwang/datasets/psg/psg_train_val.json \
  --output-root /data/jwang/datasets/kitti360_psg_smoke \
  --seq 0 \
  --max-frames 100 \
  --overwrite
```

This targets 100 training images and 10 validation images.


## Evaluation during distributed training

Periodic evaluation is rank-zero-only. Rank zero evaluates each selected image
exactly once with the underlying model while the other ranks wait at the epoch
barrier. This avoids DDP forward and metric-collective deadlocks when sample
counts are uneven.

## Evaluation performance in 0.1.6

Evaluation no longer performs Python-loop mask IoU for every pair of up to 200
relation endpoints. Panoptic matching is computed from non-overlapping segment
maps in linear time over image pixels, and predicate recall uses subject/object
bounding-box IoU. The JSON report records this metric basis explicitly.

The first evaluation sample prints `stage=forward`, `stage=postprocess`, and
`stage=metrics`, followed by `processed=1/N`, so a slow stage is visible rather
than appearing as a silent hang.


## Evaluation inference in 0.1.7

Evaluation forwards are inference-only and pass `labels=None`. Ground-truth
labels remain available to the separate PQ and predicate-recall implementation,
but the model does not invoke its training criterion. This avoids running the
triplet Hungarian matcher over potentially hundreds or thousands of generated
KITTI-360 pseudo-relations in a single frame. Evaluation JSON therefore reports
`training_loss_computed: false` and does not include an evaluation-loss field.

## Checkpoint inference and visualization

Run a checkpoint on a deterministic random set of training samples:

```bash
CUDA_VISIBLE_DEVICES=0 python3 examples/infer.py \
  --checkpoint work_dirs/psg_lidarenh_kitti360/checkpoint-0008 \
  --data-root /data/jwang/datasets/kitti360_psg \
  --annotation-file /data/jwang/datasets/kitti360_psg/annotations/psg_train_val.json \
  --lidar-manifest /data/jwang/datasets/kitti360_psg/lidar/manifest.json \
  --output-dir work_dirs/psg_lidarenh_kitti360/inference-random \
  --random-count 8 \
  --seed 42 \
  --top-k 20 \
  --score-threshold 0.25 \
  --amp
```

Select exact filtered training-dataset indices:

```bash
python3 examples/infer.py \
  --checkpoint work_dirs/psg_lidarenh_kitti360/checkpoint-0008 \
  --data-root /data/jwang/datasets/kitti360_psg \
  --annotation-file /data/jwang/datasets/kitti360_psg/annotations/psg_train_val.json \
  --lidar-manifest /data/jwang/datasets/kitti360_psg/lidar/manifest.json \
  --output-dir work_dirs/psg_lidarenh_kitti360/inference-indices \
  --indices 0 17 48
```

Select exact OpenPSG image IDs:

```bash
python3 examples/infer.py \
  --checkpoint work_dirs/psg_lidarenh_kitti360/checkpoint-0008 \
  --data-root /data/jwang/datasets/kitti360_psg \
  --annotation-file /data/jwang/datasets/kitti360_psg/annotations/psg_train_val.json \
  --lidar-manifest /data/jwang/datasets/kitti360_psg/lidar/manifest.json \
  --output-dir work_dirs/psg_lidarenh_kitti360/inference-image-ids \
  --image-ids 287 338
```

The installed command is `psg-lidarenh-infer`. Each selected sample produces a
side-by-side PNG, a complete JSON record, and an entry in `results.json`:

```text
output_dir/
├── index-000000_image-287.png
├── index-000000_image-287.json
└── results.json
```

The left panel displays ground-truth panoptic entities and relations. The right
panel displays the top-scoring predicted subject-predicate-object triplets with
subject/object masks, endpoint boxes, and confidence scores. Inference always
uses `labels=None`, so it does not invoke the expensive Hungarian training
criterion.
